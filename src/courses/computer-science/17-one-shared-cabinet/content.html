Instructions and data live in the exact same cabinet.

Every part you met in Module 16 lives inside the CPU (central processing unit). Memory, outside the CPU, is where both the program's instructions and the numbers it works on sit — addressed the same way, in the same store. This is the idea computers have been built on since the 1940s, usually named after the mathematician who described it: the Von Neumann model. This module names that idea properly, then colours in the three roads — the buses — that carry things back and forth across the link you saw in Module 16. Same machine map, now fully met.

Same deal as always: no marks, no timer, no wrong answers, nothing to hand in. Sort at your own pace, take a nudge whenever you fancy one, and nothing here ever runs out or gets marked wrong. Stars can never be taken away.

"Address 100 holds: LOAD 200" is a step for the CPU to obey — Instruction. "Address 200 holds: 19" is a plain value with nothing to obey — Data. Notice both addresses are just numbers in the same memory; nothing about the storage itself marks one as different from the other.
Ask: does this cell tell the CPU to *do* something, or just give it a *number* to use?
Once all five are sorted, look at the addresses themselves — 100, 101, 102 and 200, 201 are all just memory locations, stored and fetched in exactly the same way. The only thing that decides "instruction" or "data" is what the CPU intends to do with what it finds there — never the storage itself. That's the Von Neumann idea: one shared memory for everything.

The machine map from Module 16 — every part already met: CU (Control Unit), ALU (Arithmetic Logic Unit), PC (Program Counter), MAR (Memory Address Register), MDR (Memory Data Register), CIR (Current Instruction Register) and ACC (Accumulator). Below, the strip under the diagram lights up to show whichever road (bus) is carrying something.

Everything that moves between the CPU and memory travels along one of exactly three roads. The address bus carries a location in memory — never the value stored there, only where to find it. The data bus carries the actual thing being moved — a number, or an instruction fresh out of memory. (An instruction counts as data here: it's just being carried, not obeyed yet.) The control bus carries signals and commands only — "read this", "write that" — never a location and never a value. Tap a parcel below, then tap the road you think it travels on — watch the strip above light up to match.

Tap a parcel to begin.

"The address 104, on its way from PC into MAR" is a location — that's the Address bus. "A READ signal, telling memory to hand something over" is a command with no location and no value attached — that's the Control bus. "The value 24, arriving from memory into MDR" is an actual number being carried — that's the Data bus.
Ask what the parcel actually IS: a place, a thing, or a bare instruction to memory itself?
A place (an address) is always the Address bus. A thing being moved — a value or a fetched instruction — is always the Data bus. A command with nothing else attached, like "read" or "write", is always the Control bus.

One more pass at the same three roads. This time, each scenario is anchored to one register — PC (Program Counter), MAR (Memory Address Register), MDR (Memory Data Register) or CIR (Current Instruction Register), the tiny CPU stores you met in Module 16. Work out what that register holds, and the road follows. Pick the road for each.

"The value arriving in MDR, fresh from memory" — MDR always holds a thing, so that's the Data bus. "PC's address, on its way into MAR" — an address travelling to another address-holder, so that's the Address bus.
Remember which registers hold places (PC, MAR) and which hold things (MDR, CIR) from Module 16 — that answers most of these on its own.
MAR and PC only ever hold addresses, so anything moving into or out of them travels the Address bus. MDR and CIR hold actual values or instructions, so anything moving into or out of them travels the Data bus — even when what's moving is an instruction, not a number.

One shape, three stages, repeated millions of times a second. Fetch gets the next instruction from memory. Decode works out what it means. Execute actually carries it out. Nothing here is running yet — that's next. This is just the order, so it's already familiar once you watch it happen in slow motion. Tap a stage, then tap the position you think it belongs to.

Tap a stage to begin.

Fetch has to happen before there's anything to decode — so Fetch is 1st. Decode has to happen before the CPU knows what to execute — so Decode is 2nd. Execute is what's left — 3rd, always last.
Ask which stage has nothing to work with yet until an earlier one has finished.
Fetch → Decode → Execute, always in that order — you can't decode an instruction you haven't fetched, and you can't execute one you haven't decoded.
