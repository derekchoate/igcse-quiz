Programs feel intelligent for exactly one reason: they can take a different path.

Every line you've written so far runs top to bottom, no choices. Tonight that changes. IF reads a condition and sends the program down one of two roads — like a path splitting in front of you. Set the values on the dials below, press to walk it, and watch a lantern travel the road actually taken while the road not taken simply stays unlit.

Same deal as always: no marks, no timer, no wrong answers, nothing to hand in. Every fork is yours to walk however you like — take a nudge whenever you fancy one. Stars can never be taken away.

Cinemas price tickets by age. One condition, two prices — the simplest fork there is. IF asks the question, THEN names what happens when it's true, ELSE names what happens when it's false, and ENDIF closes the fork back up. Pick an age below — 19 is on the list, in case you fancy sending yourself through — then step the lantern through and watch which road lights up.

IF Age >= 18
THEN
Price ← 15
OUTPUT "Adult ticket", Price
ELSE
Price ← 8
OUTPUT "Child ticket", Price
ENDIF
Feed it 12. The diamond asks "is 12 ≥ 18?" — no, so the lantern takes the ELSE road: Price becomes 8, and it prints "Child ticket 8". Reset and feed it 25 instead: now the question is true, the lantern takes the THEN road, and it prints "Adult ticket 15". Same fork, same diamond — only the input changed which road lit up.
Read the diamond as a plain yes/no question about the age you fed it. Whichever answer it gives, exactly one of the two roads lights up — never both, never neither.
Try your own age — 19. 19 ≥ 18 is true, so THEN fires: Price ← 15, "Adult ticket". Now imagine feeding it 10 instead — 10 ≥ 18 is false, so ELSE fires: Price ← 8, "Child ticket".

Sometimes an IF has no ELSE at all — nothing is written for what happens when the answer is no. Cambridge allows that, and it does not mean the "no" road vanishes. It just means that road leads straight past, doing nothing, before rejoining the rest of the program. Below is a canteen loyalty stamp with no ELSE in sight. Walk both ticket types and watch the "no" road all the same.

IF Ticket = "Adult"
THEN
Stamps ← Stamps + 1
ENDIF
OUTPUT "Enjoy the show!"

Notice: there is no ELSE line at all. Walk it with a Child ticket and see what the "no" road actually does.

Feed it "Adult" — the diamond is true, so Stamps goes up by one, then the road rejoins and prints "Enjoy the show!". Now feed it "Child" — the diamond is false, and the lantern still has to go somewhere: it takes the quiet "do nothing" road, skips straight past the stamp, and rejoins at the very same print line. Nothing broke — that quiet road was always there, it just never got written as words.
Look at the flowchart, not just the code. The "no" arrow out of the diamond leads somewhere in the diagram even though the pseudocode above never says the word ELSE.
"No ELSE written" means "do nothing extra" — not "no road". Every diamond has exactly two arrows leaving it, always, whether or not the pseudocode bothers to name the quiet one.

Cambridge has no "ELSE IF" keyword — to test a second condition you nest a fresh IF inside the ELSE, and a third inside that ELSE, and so on. It works, but it gets deeper and harder to read with every extra option. CASE OF tests one variable against several values and stays flat, no matter how many options there are. A condition can combine two questions at once. AND only opens the gate when both switches are on. OR opens it as soon as either one is. The gate reads OPEN when the whole condition is true, and SHUT when it's false. Flip the two switches below, pick AND or OR, and watch the gate.

Switch to AND, then turn on only Raining — the gate stays shut, because AND needs Raining AND Cold both true, and Cold is still off. Now also turn on Cold — the gate opens, the coat rule fires. Switch to OR with the same two switches on: it was already open, no surprise. Now turn Cold back off, staying on OR — one switch alone is enough, so the gate stays open: OR only needs one side true.
AND needs both switches on; OR needs at least one. Rain AND cold → coat. It's raining but warm — does the rule fire?
No: AND fails if either part fails, even if the other part is true. Try it on the switches — one switch on is never enough for AND, only for OR.

NOT takes whatever a condition says and flips it — true becomes false, false becomes true. It doesn't need a second condition or a gate with two switches; it just turns the one sign around. Flip the switch and the NOT toggle below and watch both the raw answer and the flipped one — NOT only ever cares about true and false, never about whether the result still sounds sensible in plain English.

Find every combination…

Raining is on, NOT is off: the condition reads "Raining" plainly — true, so it's umbrella weather. Now switch NOT on, Raining still on: the condition reads "NOT Raining" — Raining is true, so NOT flips it to false, and it's t-shirt weather instead. The rain didn't change; only the sign in front of it did.
Read NOT as "the opposite of whatever follows". Check Raining's raw value first, then just flip it once NOT is switched on.
Raining off, NOT on: "NOT Raining" flips false to true — the condition fires, so it prints umbrella weather, even though it isn't actually raining. Raining off, NOT off: "Raining" stays false, so it prints t-shirt weather, matching what you'd expect. NOT only ever flips the true/false value — it has no idea whether the result still makes sense outside the code.
