Here's the one rule a trace table runs on: it gets one row per line, and a box only gets a new number in the one column that line actually changes — every other column in that row stays a dash, not a repeat of its old number. The box that's next always has a soft outline around it, and its choices are already waiting just below — pick the number you think belongs there, and watch the box glow amber the moment it matches what the program actually did. Nothing is marked wrong — an unmatched pick just leaves the box quiet, with a soft note on where to look again.

Score is 10 after line 1. Line 3 says Score ← Score + Bonus — so line 3's new Score is the old Score (10) plus Bonus (5), not Bonus on its own and not the old 10 repeated.

A loop gives a trace table two rows per lap, not one — the FOR line is the one that actually sets the counter to its next value, so that's the row Count gets its new number on, every single lap. The body line underneath is a separate row, where Total picks up the new Count and uses it. NEXT itself doesn't get a row — it doesn't create a new value, it just sends the loop back round.

Line 1: Total starts at 0, Count still a dash — the loop hasn't begun. Lap 1 · FOR: Count becomes 1, on the FOR line itself. Lap 1 · Total: Total becomes 0 + 1 = 1, on the body line underneath. Lap 2 · FOR: Count becomes 2. Lap 2 · Total: Total becomes 1 + 2 = 3. Lap 3 · FOR: Count becomes 3. Lap 3 · Total: Total becomes 3 + 3 = 6. Lap 4 · FOR: Count becomes 4. Lap 4 · Total: Total becomes 6 + 4 = 10. After lap 4, NEXT Count makes Count 5 — 5 TO 4 is false, so the loop simply stops there, no new row needed for a lap that never runs. Line 5's OUTPUT prints 10.
Watch which line each column belongs to — Count only ever gets a new number on the FOR row, since that's the line that actually sets it. Total only ever gets a new number on the row underneath, since that's the line that actually adds to it.
Lap 3 · FOR: Count becomes 3. Lap 3 · Total: Total becomes whatever it was after lap 2 (3), plus this lap's Count (3) — 6. Each lap's Total always builds on the lap right before it.

Cambridge's MOD is written as a function: MOD(Num, 2) gives the remainder when Num is divided by 2. Num gets its new number on the FOR row, every single lap, no exceptions. Total is different: this program only adds Num to Total on laps where that remainder is 0 — the even laps — and even then, on a row of its own, further down at the body line. On the odd laps, that second row simply doesn't appear: Num still moved on the FOR row, so the lap still happened, it's just that nothing below it ever changed.

Line 1: Total starts at 0. Lap 1 · FOR (Num 1): Num becomes 1 — MOD(1, 2) = 1, not 0, so THEN never fires and there's no Total row this lap. Lap 2 · FOR (Num 2): Num becomes 2. Lap 2 · Total: MOD(2, 2) = 0, so Total becomes 0 + 2 = 2. Lap 3 · FOR (Num 3): Num becomes 3 — odd again, no Total row. Lap 4 · FOR (Num 4): Num becomes 4. Lap 4 · Total: even, so Total becomes 2 + 4 = 6. Lap 5 · FOR (Num 5): Num becomes 5 — odd, no Total row. OUTPUT prints 6. Every lap still got its FOR row, whether or not that lap went on to earn a Total row too.
Num changes on every lap's FOR row, without exception. Total only ever gets a row of its own when MOD(Num, 2) = 0 is actually true that lap — on every lap where it's false, there's simply no Total row that lap, but the FOR row still belongs there.
A missing row in a trace table never means "nothing happened this lap" — the FOR row is always there, proving the lap ran. It only ever means one particular line further down had nothing new to do that time.
