The machine map is back, this time with a crank. A strip above the log names whichever bus is carrying something at that instant — the same roads you coloured in Module 17. Press the crank once per step and watch PC especially closely across the whole fetch — something about its timing is easy to assume wrong.

Crank once: PC's address, 100, travels the address bus into MAR. Crank again: PC increments to 101 — already pointing at the NEXT instruction, before this one has even reached the CIR. Crank again: the control unit sends a READ signal along the control bus, telling memory to hand over what's stored at address 100. Crank again: memory sends back the instruction there — "LOAD 200" — along the data bus into MDR. Crank once more: MDR's contents copy into CIR. The instruction has arrived, ready to be decoded — and PC changed two steps before that, not at the end.
Watch PC across one complete fetch. Did it change before or after the instruction arrived in the CIR?
It changes during fetch — it's already pointing at the next instruction while this one is still on its way in. That's the whole point of a program counter: it never falls behind, even mid-cycle.

Picture the CPU has already fetched its next instruction into the CIR: ADD, plus the address where the amount to add is stored. Its accumulator — ACC, the CPU's one working notepad for numbers — currently holds 19, your age. Pick an amount below, start the ADD, then crank through decode and execute.

Try an amount that's…

Set the amount to 5 and press "Start this ADD". Crank once: the control unit decodes CIR — "ADD 201" means add whatever's stored at address 201 to ACC. Crank again: 201 travels the address bus into MAR. Crank again: memory sends back the value there, 5, along the data bus into MDR. Crank once more: the ALU adds MDR's 5 to ACC's 19. ACC updates to 24 — right in front of you. Notice the ALU did the sum, but it's ACC that keeps hold of the answer afterwards; the ALU itself doesn't remember a thing once it's done.
Try a small amount (under 10) and then a large one (15 or more) — does ACC update the same way either time?
It's tempting to think the ALU is where the answer lives afterwards, since it's the ALU that does the actual adding. It isn't — the ALU calculates for one instant and then forgets; ACC is the register that actually holds the running result.

Here's a tiny three-line program, at the concept level (never mind the exact machine code — that's a later module). Line 1, LOAD 200: copy whatever's stored at address 200 into ACC. Line 2, ADD 201: add whatever's stored at address 201 to ACC. Line 3, STORE 202: copy ACC's value out to address 202. Address 200 holds 19 (your age); address 201 holds 6 — the very cells you sorted in Module 17. Before you crank a single step, take a private guess at what ACC will hold once all three lines have run. Nobody sees this guess but you — there's no wrong answer here, only a chance to check your own thinking against the machine.

Guess: 19

Line 1 fetches, decodes and executes LOAD 200 — 19 copies straight into ACC (no ALU needed, LOAD is just a delivery). Line 2 fetches, decodes and executes ADD 201 — the ALU adds 6 to ACC's 19, making 25. Line 3 fetches, decodes and executes STORE 202 — ACC's 25 copies out to address 202. STORE never changes ACC itself; it only copies ACC's value elsewhere. Final answer: 25.
Work out what LOAD and ADD actually do to ACC, in order, before you crank anything.
LOAD 200 copies 19 into ACC. ADD 201 adds 6 to whatever ACC already holds. STORE just copies ACC's value out to memory — it never changes ACC's value at all.
