Five little algorithms run the world's paperwork. You already have every piece they're made of.

Same wall as last time — one name, six numbered compartments — but this time you clip different "lenses" onto it. A totalling lens watches a running sum grow. A counting lens only reacts when a condition is true. A challenger lens crowns a champion. A patient-finger lens checks compartment after compartment for one value. And a swapping lens nudges neighbours past each other until the whole wall settles into order. Same wall, same FOR loop underneath, five completely different jobs — that's the whole trick of this module.

Six rounds of a mobile game, scores logged in Scores : ARRAY[1:6] OF INTEGER. Total starts at 0, and every lap of the loop adds one more compartment onto it — Total ← Total + Scores[Index]. Press Step to add one compartment at a time, or Run to send it round the whole wall, and watch Total climb.

Press Step: Index is 1, Scores[1] is 62, so Total ← 0 + 62 = 62. Press Step again: Index is 2, Scores[2] is 45, so Total ← 62 + 45 = 107. Total never gets reset partway through — it just keeps absorbing one more compartment every lap, until all six have been added in. Once the loop ends, Average appears too — it's simply the final Total divided by 6, the number of compartments that went into it.
Before the loop starts, Total is 0 — not empty, not undefined, a real zero. That's what makes "add this compartment onto whatever Total already holds" safe to do from the very first lap.
Watch the readout after every single Step — Total only ever grows, one compartment's value at a time, and the compartment it just added is exactly the one that lit up.

Same wall, different lens. This time Count only moves when a condition is true: IF Scores[Index] > 50. A compartment that fails the condition still gets visited — the loop never skips one — it just doesn't earn Count anything. Step or Run through all six and see how many clear 50.

Index 1: Scores[1] is 62. 62 > 50 is true, so Count ← 0 + 1 = 1. Index 2: Scores[2] is 45. 45 > 50 is false — THEN never fires, Count stays 1. Index 3: Scores[3] is 78, true again, Count becomes 2. Keep going and the loop visits every compartment exactly once, but Count only climbs on the ones that meet the condition — by the end it settles on 4.
Every compartment gets checked, even the ones that fail — the loop doesn't jump over anything. It's Count that stays still on a failing compartment, not the loop.
Compare this to Discovery 1: Total added something on every single lap, no exceptions. Count only adds 1 on the laps where the IF is true — that's the entire difference between the two lenses.

Champion starts out as whatever sits in the very first compartment — no contest needed for that one, it simply holds the title until someone beats it. Every compartment after it steps up as a Challenger: if it's bigger than the current Champion, it takes the crown; if not, the Champion keeps it and the wall moves on. Step or Run through all five challengers and see who's left standing.

Champion ← Scores[1] = 62, crowned with no contest. Challenger 45 (compartment 2): 45 > 62 is false — Champion stays 62. Challenger 78 (compartment 3): 78 > 62 is true — new Champion, 78. Challenger 51: 51 > 78 is false, no change. Challenger 90: 90 > 78 is true — Champion becomes 90. Challenger 33: 33 > 90 is false. Final Champion: 90 — it only ever changes hands when a challenger genuinely beats whoever currently holds it.
The very first compartment never has to prove anything — it's crowned Champion automatically, before any comparing starts at all.
From compartment 2 onward, ask exactly one question each lap: is this challenger bigger than the current Champion? Only "yes" changes anything.

What if, to save a step, Champion had started at 0 instead of Scores[1]? On an everyday wall like this one that quietly still works, because every score here is above 0 anyway. Flip to an all-negative wall below and watch that shortcut fall apart.

Five compartments this time, and this lens does something new: it compares two neighbours, and swaps them if the left one is bigger than the right. Press Shuffle to scramble the row into your own mess, then Step or Run — each pass sweeps left to right once, and a "swaps this pass" tally counts how many neighbour-swaps actually happened. Watch that tally across passes: it has something to tell you about when the row is finally sorted.

Say the row reads 4, 1, 5, 2, 3. Compare compartments 1 and 2: 4 > 1, so they swap — 1, 4, 5, 2, 3. Compare 2 and 3: 4 > 5 is false, no swap. Compare 3 and 4: 5 > 2, swap — 1, 4, 2, 5, 3. Compare 4 and 5: 5 > 3, swap — 1, 4, 2, 3, 5. That's Pass 1 done, 3 swaps. Keep running passes and the biggest values keep bubbling rightward — eventually a whole pass goes by with the swap tally sitting at 0. Nothing to fix means the row is already sorted, and that's the exact signal that stops the algorithm.
Watch the swap tally on the last pass you run, not just the row itself.
Zero swaps happened on that pass. What must be true of every neighbouring pair on the whole row for that to happen?
Already in order — that's the signal to stop, and it's how the algorithm knows the row is sorted without ever needing to "see" the whole thing at once. One pass with nothing to swap is proof enough.

Line 1 has to be "Largest ← Scores[1]" — nothing later can compare against a champion that doesn't exist yet, so this always comes first. Line 2 starts the sweep, "FOR Index ← 2 TO 5" — it begins at 2 because compartment 1 is already spoken for. Lines 3–6 are the IF/THEN/update/ENDIF block that only replaces Largest when something bigger turns up. Line 7 closes the loop, "NEXT Index", and Line 8, "OUTPUT Largest", only makes sense once the sweep is completely finished — it has to be last.
Start with the two lines you can place with total confidence: whichever one sets up the very first champion, and whichever one prints the final answer. One of those has to be first, the other has to be last.
The IF, THEN, the update line, and ENDIF always travel together as one block, in that order — place the FOR line just before that block starts, and NEXT Index just after it ends.

Notice what just happened — a twenty-fifth time

Five little algorithms, and every single one of them was the same FOR loop wearing a different job. Totalling just kept adding. Counting added a condition before it would move. The champion-and-challenger game only ever changed hands when something genuinely beat it. The patient finger stopped the instant it found a match — and when it didn't, checking every last compartment was the entire point, not a failure of one. And the bubbles: neighbours compared, sometimes swapped, and one whole pass with nothing left to swap was proof, all by itself, that the row was done. You even took the very first of those apart and rebuilt it, line by line, from a shuffled pile.

These five patterns show up again and again in real programs — you'll meet them wearing new costumes for the rest of this course. (One small aside, purely for interest: once a wall is already sorted, cleverer ways exist to search it far faster than checking one compartment at a time — not part of 0478, and not something you need to build here, just worth knowing they're out there.)
