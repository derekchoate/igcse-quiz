Five little algorithms run the world's paperwork. You already have every piece they're made of.

You know this setup already — one name, numbered compartments. This time there are six of them.

The FOR loop that sweeps across them stays exactly the same each time. What changes is the job it's given:

  1. Totalling watches a running sum grow.
  2. Counting only reacts when a condition is true.
  3. Challenging crowns a champion.
  4. Searching checks compartment after compartment for one value.
  5. Swapping nudges neighbours past each other, until the whole row settles into order.

Same idea, same FOR loop underneath, five completely different jobs. That's the whole trick of this module.

Same deal as always: no marks, no timer, no wrong answers, nothing to hand in. Step through at your own pace or let it run. A search that finds nothing is still a real result, not a miss. Take a nudge whenever you fancy one. Stars can never be taken away.

Six rounds of a mobile game, scores logged in Scores : ARRAY[1:6] OF INTEGER. Total starts at 0. Every lap of the loop adds one more compartment onto it — Total ← Total + Scores[Index].

Press Step to add one compartment at a time. Or press Run to send it through every compartment. Either way, watch Total climb.

Press Step: Index is 1, Scores[1] is 62, so Total ← 0 + 62 = 62. Press Step again: Index is 2, Scores[2] is 45, so Total ← 62 + 45 = 107. Total never gets reset partway through. It just keeps absorbing one more compartment every lap, until all six are in. Once the loop ends, Average appears too. It's the final Total divided by 6 — the number of compartments that went in.
Before the loop starts, Total is 0 — not empty, not undefined, a real zero. That's why adding a compartment onto Total is safe from the very first lap.
Watch the readout after every Step. Total only grows — one compartment's value at a time. The compartment it just added is exactly the one that lit up.

Same compartments, different job. This time Count only moves when a condition is true: IF Scores[Index] > 50. A compartment that fails the condition still gets visited. The loop never skips one. It just doesn't earn Count anything.

Step or Run through all six and see how many clear 50.

Index 1: Scores[1] is 62. 62 > 50 is true, so Count ← 0 + 1 = 1. Index 2: Scores[2] is 45. 45 > 50 is false — THEN never fires, Count stays 1. Index 3: Scores[3] is 78, true again, Count becomes 2. Keep going, and the loop visits every compartment exactly once. Count only climbs on the ones that meet the condition. By the end, it settles on 4.
Every compartment gets checked, even the ones that fail — the loop doesn't jump over anything. It's Count that stays still on a failing compartment, not the loop.
Compare this to Discovery 1: Total added something on every single lap, no exceptions. Count only adds 1 on the laps where the IF is true. That's the entire difference between the two jobs.

Champion starts out as whatever sits in the very first compartment. No contest needed — it simply holds the title until someone beats it.

Every compartment after it steps up as a Challenger. If it's bigger than the current Champion, it takes the crown. If not, the Champion keeps the title, and the loop moves on.

Step or Run through all five challengers and see who's left standing.

Champion ← Scores[1] = 62, crowned with no contest. Challenger 45 (compartment 2): 45 > 62 is false — Champion stays 62. Challenger 78 (compartment 3): 78 > 62 is true — new Champion, 78. Challenger 51: 51 > 78 is false, no change. Challenger 90: 90 > 78 is true — Champion becomes 90. Challenger 33: 33 > 90 is false. Final Champion: 90 — it only ever changes hands when a challenger genuinely beats whoever currently holds it.
The very first compartment never has to prove anything. It becomes Champion right away, before any comparing starts.
From compartment 2 on, ask one question each lap: is this challenger bigger than the current Champion? Only "yes" changes anything.

Optional extra — a classic trap

What if, to save a step, Champion had started at 0 instead of Scores[1]? With these compartments, it still works — every score here is already above 0. Flip the toggle below to all-negative numbers, and watch that shortcut fall apart.

Type a Target below. Then press Step or Run to send a finger through the compartments, one at a time. At each one, it asks the same question: is this the Target? The instant it matches, the finger stops — no need to check what's left.

If it checks the last compartment without a match, that's not a mistake. It's a complete, useful answer. The value genuinely isn't there. The only way to know that for certain is to check every compartment.

Five compartments this time. This job does something new: it compares two neighbours. It swaps them if the left one is bigger than the right.

Press Shuffle to scramble the row into your own mess. Then press Step or Run. Each pass sweeps left to right once. A "swaps this pass" tally counts how many neighbour-swaps happened.

Watch that tally across passes. It has something to tell you about when the row is finally sorted.

Say the row reads 4, 1, 5, 2, 3. Compare compartments 1 and 2: 4 > 1, so they swap — 1, 4, 5, 2, 3. Compare 2 and 3: 4 > 5 is false, no swap. Compare 3 and 4: 5 > 2, swap — 1, 4, 2, 5, 3. Compare 4 and 5: 5 > 3, swap — 1, 4, 2, 3, 5. That's Pass 1 done, 3 swaps. Keep running passes, and the biggest values keep bubbling rightward. Eventually, a whole pass goes by with the swap tally sitting at 0. Nothing to fix means the row is already sorted. That's the exact signal that stops the algorithm.
Watch the swap tally on the last pass you run, not just the row itself.
Zero swaps happened on that pass. What must be true of every neighbouring pair on the whole row for that to happen?
Already in order — that's the signal to stop. The algorithm knows the row is sorted without ever "seeing" the whole thing at once. One pass with nothing to swap is proof enough.

The program, line by line
Shuffled lines

Drag a line across, or tap one and then the slot it belongs in.

Line 1 has to be "Largest ← Scores[1]". Nothing later can compare against a champion that doesn't exist yet — so this always comes first. Line 2 starts the sweep: "FOR Index ← 2 TO 5". It begins at 2 because compartment 1 is already spoken for. Lines 3–6 are the IF/THEN/update/ENDIF block that only replaces Largest when something bigger turns up. Line 7 closes the loop: "NEXT Index". Line 8, "OUTPUT Largest", only makes sense once the sweep is completely finished — it has to be last.
Start with the two lines you can place with total confidence. One sets up the very first champion — that one has to come first. The other prints the final answer — that one has to come last.
The IF, THEN, the update line, and ENDIF always travel together, as one block, in that order. Place the FOR line just before that block starts. Place NEXT Index just after it ends.

Notice what just happened — a twenty-fifth time

Five little algorithms, and every single one of them was the same FOR loop wearing a different job. Totalling just kept adding. Counting added a condition before it would move.

The champion-and-challenger game only ever changed hands when something genuinely beat it. The patient finger stopped the instant it found a match. When it didn't, checking every last compartment was the entire point — not a failure of one.

And the bubbles: neighbours compared, sometimes swapped. One whole pass with nothing left to swap was proof, all by itself, that the row was done. You even took the very first of those apart and rebuilt it, line by line, from a shuffled pile.

These five patterns show up again and again in real programs. You'll meet them wearing new costumes for the rest of this course.

(One small aside, just for interest. Once compartments are already sorted, cleverer ways exist to search them — faster than checking one at a time. Not part of 0478. Not something you need to build here. Just worth knowing they're out there.)
