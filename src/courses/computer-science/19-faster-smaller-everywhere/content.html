Why does a phone that costs RM 3,000 feel fast? And why does your washing machine — also a computer — cost less than the phone case? Clock speed is how many times a second a CPU's fetch–decode–execute loop from Module 16 turns over. In a real machine that's billions of times a second — far too fast to watch — so here it's slowed right down to a rate you can actually see. Turn the dial to set a tick rate, then press start: a metronome ticks at that steady rate until it reaches 8 ticks, and the clock keeps time so you can see exactly how long 8 ticks took. Try a slow rate and a fast one — the gap between them is clock speed, in miniature. (Worth knowing up front: real chips don't always speed up in exact proportion to their clock speed — heat and other bottlenecks get in the way — but this discovery isolates clock speed on its own, with everything else held steady.)

Pick a speed, then press start.

Try a speed that's…

Dial set to 1 tick/second, press start: the metronome ticks once a second, and reaching 8 ticks takes 8 real seconds. Reset the dial to 4 ticks/second and run it again: the same 8 ticks now take just 2 real seconds. Nothing else changed — same 8 ticks, same metronome — only the rate the crank turns over changed, and the total time changed to match.
Run the slowest setting first and actually watch the seconds tick by, then run the fastest setting and compare. What stayed exactly the same between the two runs, and what was the only thing that changed?
The number of ticks needed (8) never changes. Only the rate changes — double the ticks per second, and the same 8 ticks land in half the time. That proportional relationship is exactly what "clock speed" means: more ticks, more often, in the same second.

A core is a whole separate worker inside the CPU, able to fetch, decode and execute on its own — more cores means more instructions happening at the same instant, not just the same one happening faster. Below are two workloads, both worth 12 ticks in total: one long task that cannot be broken into pieces (think: one instruction that depends on the result of the one before it), and many small tasks — 12 equal one-tick pieces that can be shared out however you like. Pick a workload, set the number of cores, and run it. Try the long task with just one core, then try it again with several — and watch what does (and doesn't) change.

    Try…

    One long task, 1 core: finishes in 12 ticks — a single worker, doing all 12 ticks' worth alone. Same long task, 4 cores: still 12 ticks — three of the four workers stand around with nothing to do, because one indivisible task can't be handed out to a team. Now switch to many small tasks with 4 cores: the 12 one-tick pieces split evenly, 3 per worker, and the whole thing finishes in just 3 ticks. Extra cores only pay off when the work itself can actually be divided up.
    Give the long single task four workers instead of one. Time it — has anything actually gotten faster?
    No faster at all — the task can't be split, so three of the four cores just sit idle. Extra cores only help when the work is genuinely parallel, like the many-small-tasks pile.

    Cache is a small, very fast storage area sitting right next to the CPU, used to keep hold of data and instructions it has recently needed — like a shelf right beside a workbench, instead of a storeroom down the hall. Below is a workload: fetch the same tool 5 times in a row. With the cache off, every single fetch means the full walk to the storeroom. With the cache on, the first fetch still costs a full trip — but once that tool is on the shelf, every repeat fetch is nearly free. Toggle the cache and run the workload both ways.

      Try…

      Cache off, fetch the same tool 5 times: each trip costs 4 ticks, so 5 × 4 = 20 ticks total — every single fetch walks all the way to the storeroom, even though it's the same tool each time. Cache on, same workload: the first fetch still costs 4 ticks (it has to be brought in from the storeroom once), but the next four fetches cost just 1 tick each, since the tool is already sitting on the shelf — 4 + (4 × 1) = 8 ticks total. Same workload, less than half the time, purely from not re-fetching something already close by.
      Run the workload with the cache off, then flip it on and run the exact same workload again. What's different about the very first fetch compared with the rest?
      The first fetch always costs full price either way — the tool has to arrive from the storeroom at least once. The saving only appears on the repeats, because the cache holds onto what was reused. If every fetch needed a different tool instead, there'd be nothing sitting on the shelf worth reusing, and the cache wouldn't help at all.

      Every CPU is built to understand a fixed list of commands, and absolutely nothing outside that list — that whole list is its instruction set, and every command in it counts as machine code. You've already met three of a real instruction set's commands, back in Module 16's three-line program: LOAD, ADD, STORE. Here's a fourth, SUBTRACT, alongside those same three again. Tap a job below, then tap the command you think does it — or drag it straight across.

      Tap a job to begin.

      "Copies a value from memory into the accumulator, replacing whatever was there" describes LOAD. "Copies the accumulator's current value out to memory, leaving the accumulator unchanged" describes STORE — notice LOAD and STORE move data in opposite directions. "Adds a value to whatever the accumulator already holds" describes ADD, and "Takes a value away from whatever the accumulator already holds" describes SUBTRACT — a matching pair, opposite operations, same one register.
      Ask two things about each job: does it move a value in, move a value out, or change a value that's already there? And if it changes a value, is it adding or taking away?
      LOAD and STORE are the direction pair — LOAD brings a value in, STORE sends one out, and neither one does any arithmetic. ADD and SUBTRACT are the arithmetic pair — both change whatever's already in the accumulator, just in opposite directions.

      An embedded system is a computer built to perform one dedicated function — the same job, every time it's switched on, for its entire working life. That's different from a general-purpose computer, built to perform many different functions depending on what you install or open on it. Sort the household objects below into the two bins first. Embedded systems usually share two more traits worth knowing, even though the syllabus's real test is dedicated function: they typically run on firmware — software built permanently into the device's own hardware, rather than something you install (you'll meet firmware properly in a later module) — and they're typically built for low power, sipping very little electricity so they can run for a long time, sometimes years, without needing much energy. Once you've sorted the objects, match those three traits to their descriptions in the second board.

      Tap a description to begin.

      A rice cooker only ever cooks rice, from the day it's switched on to the day it's thrown out — one dedicated function, so it sorts as an embedded system. A laptop can be a word processor one moment and a video player the next, depending entirely on what you open — many different functions, so it sorts as general-purpose. For the traits: "built to do one job, and only that job, for its whole working life" describes dedicated function; "software built permanently into the device's hardware, rather than installed like an app" describes firmware; "designed to run for a very long time on very little electricity" describes low power.
      For each object, ask one question: does this thing do one job forever, or does what it does depend on what you install or choose to open on it?
      Size is a trap here — a smartphone is small but general-purpose (it runs whatever apps you choose), while some embedded systems are large (a car's engine control unit). The only question that actually sorts them is dedicated function versus many functions.
