Real programs aren't one long scroll. They're built from named, reusable blocks.

Every discovery so far has lived inside one long stretch of steps. Tonight that changes: picture a small workshop of machines, each one built once and reused as many times as a program needs. A procedure is a machine with input hoppers — its parameters — that simply does something. A function is the same idea with one extra part: an output chute that sends a value back out, via RETURN. The main program is a conveyor that visits these machines in order, a bit like the loops from Module 12 — except here each stop is a whole named block, not just one line repeating. And a variable declared inside a machine lives only inside its own glass case, born the moment the machine starts, gone the moment it stops.

Same deal as always: no marks, no timer, no wrong answers, nothing to hand in. Swapped hoppers and vanished variables are just things the workshop does — never you getting something wrong. Take a nudge whenever you fancy one. Stars can never be taken away.

A procedure is a named, reusable block of steps. Cambridge writes one like this: PROCEDURE Greet(Name : STRING), then its steps, then ENDPROCEDURE. The Name : STRING inside the brackets is a parameter — a hopper built into the machine's design, waiting to receive a value. Every time you actually run the machine, you pour a real value into that hopper — that's called an argument. Cambridge writes "run this machine, with this value in its hopper" as CALL Greet("Amir"). Feed a name into the hopper below and press the button. Then try it again with a different name, and a third time with another — same machine, same steps, every time.

A third name — maybe your own — and you've called one machine three times without writing it out three times.

The hopper itself is named Name — but the real word you type in is called an argument, not a parameter. Name is a permanent part of the machine's design; whatever you actually type is a one-off value poured in for this particular call.

A procedure can only ever do something — OUTPUT, mostly. A function is built almost the same way, except it also has an output chute: a value comes back out and lands on the conveyor, for whoever called it to use however they like. Cambridge writes the header with RETURNS <data type>, and the last thing inside is usually RETURN <value> — the value sent back. One more rule, stated exactly: you never write CALL in front of a function. A function is only ever called from inside an expression — OUTPUT Initial(Name), never CALL Initial(Name). A function's RETURN doesn't print anything by itself — something outside has to use the value, by outputting it, storing it, or comparing it. Otherwise it simply goes nowhere.

A machine with two hoppers fills them in the exact order you hand values over — the first argument lands in the first hopper, the second in the second, no exceptions. PROCEDURE Introduce(Name : STRING, Job : STRING) has two hoppers that both happen to accept the same data type, STRING — which means nothing stops you handing the arguments over in the wrong order. The machine has no way to know what a value is supposed to mean, only which hopper it landed in. Cambridge's rule, stated exactly: a variable DECLAREd inside a procedure or function is local — it lives inside that machine's glass case, born the moment the machine starts, belonging to that one machine alone. A variable declared out in the open, outside every machine, is global — it sits on the factory floor, reachable from anywhere, for as long as the whole program runs. (Some other languages default variables to global unless told otherwise — Cambridge pseudocode never does; where a variable is declared decides everything.) Procedures and functions are built almost identically — the one tell that never lies is the header line. If it says RETURNS <data type>, it's a function, and somewhere inside there'll be a RETURN. If it doesn't, it's a procedure. Tap a blueprint below, then tap the pile you think it belongs on — a mismatched pick just bounces back so you can look again; nothing here is ever marked wrong.

ShowMenu has no RETURNS anywhere in its header — Procedure pile. Double(N : INTEGER) RETURNS INTEGER — the header says RETURNS, so Function pile, no need to even read the body. Same tell, every single time: RETURNS present → Function; RETURNS absent → Procedure.
Ignore everything except the very first line of each blueprint — the header. You're looking for one word.
RETURNS is the whole tell. It doesn't matter how many parameters a blueprint has or what it's named — RETURNS on the header line means Function, every time; its absence means Procedure, every time.
