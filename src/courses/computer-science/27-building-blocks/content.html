Real programs aren't one long scroll. They're built from named, reusable blocks.

Every discovery so far has lived inside one long stretch of steps. Tonight that changes.

Picture a small workshop of machines. Each one is built once, then reused as many times as a program needs.

A procedure is a machine with input hoppers. Those hoppers are called parameters. A procedure simply does something.

A function is the same idea, with one extra part: an output chute. The chute sends a value back out, using RETURN.

The main program is a conveyor. It visits these machines in order, a bit like the loops from Module 12. But here, each stop is a whole named block — not just one line repeating.

A variable declared inside a machine lives only inside its own glass case. It's born the moment the machine starts. It's gone the moment the machine stops.

Same deal as always: no marks, no timer, no wrong answers, nothing to hand in. Swapped hoppers and vanished variables are just things the workshop does — never you getting something wrong. Take a nudge whenever you fancy one. Stars can never be taken away.

A procedure is a named, reusable block of steps. Cambridge writes one like this: PROCEDURE Greet(Name : STRING), then its steps, then ENDPROCEDURE.

The Name : STRING inside the brackets is a parameter. It's a hopper built into the machine's design, waiting to receive a value.

Every time you run the machine, you pour a real value into that hopper. That's called an argument. Cambridge writes "run this machine, with this value in its hopper" as CALL Greet("Amir").

The hopper itself is named Name. But the real word you type in is called an argument, not a parameter. Name is a permanent part of the machine's design. Whatever you actually type is just a one-off value, poured in for this one call.

A procedure can only ever do something — mostly OUTPUT. A function is built almost the same way, but with one extra part: an output chute.

A value comes back out of that chute and lands on the conveyor. Whoever called the function can use that value however they like.

Cambridge writes the header with RETURNS <data type>. The last thing inside is usually RETURN <value> — the value sent back.

One more rule, stated exactly: you never write CALL in front of a function. Instead, a function is always called from inside an expression, like OUTPUT Initial(Name). Never CALL Initial(Name).

A function's RETURN doesn't print anything by itself. Something outside has to use the value — by outputting it, storing it, or comparing it. Otherwise, it simply goes nowhere.

A machine with two hoppers fills them in the exact order you hand values over. The first argument lands in the first hopper. The second lands in the second. No exceptions.

Cambridge's rule, stated exactly: a variable DECLAREd inside a procedure or function is local. It lives inside that machine's glass case. It's born the moment the machine starts. It belongs to that one machine alone.

A variable declared out in the open, outside every machine, is global. It sits on the factory floor, reachable from anywhere. It stays there for as long as the whole program runs.

Some other languages default variables to global, unless told otherwise. Cambridge pseudocode never does — where a variable is declared decides everything.

Procedures and functions are built almost identically. The one tell that never lies is the header line.

If it says RETURNS <data type>, it's a function — and somewhere inside, there'll be a RETURN. If it doesn't, it's a procedure.

Tap a blueprint below, then tap the pile you think it belongs on. A mismatched pick just bounces back, so you can look again. Nothing here is ever marked wrong.

Tap a blueprint to begin.

ShowMenu has no RETURNS anywhere in its header — Procedure pile. Double(N : INTEGER) RETURNS INTEGER — the header says RETURNS, so Function pile. No need to even read the body. Same tell, every single time: RETURNS present means Function. RETURNS absent means Procedure.
Ignore everything except the very first line of each blueprint — the header. You're looking for one word.
RETURNS is the whole tell. It doesn't matter how many parameters a blueprint has, or what it's named. RETURNS on the header line means Function, every time. Its absence means Procedure, every time.

Notice what just happened — a twenty-seventh time

You built a procedure with one hopper, and called it three times without ever rewriting it. That's exactly what "reusable" buys you.

You turned that same idea into a function. You watched a value travel back through RETURN onto the conveyor. Then you saw for yourself: a returned value is only used if something outside the machine chooses to use it.

You fed two hoppers in order, then swapped the arguments. You met the polite chaos of a machine that has no idea what its values are supposed to mean.

You watched a local variable get born inside a glass case. Then you watched it vanish, the moment its machine stopped. Right alongside it, a global variable on the factory floor kept its value the whole time.

And you sorted six blueprints into two piles, using nothing but one header word.
