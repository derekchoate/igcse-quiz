Every program you've written since Module 1 runs on one small machine with a name for every part.

Open up a CPU (central processing unit — the chip that actually runs your programs) and you find seven named parts. In that same computer, you will also find another critial component: memory (RAM), holding the instructions and data a program needs. This machine has been built the same way since the 1940s. This module meets it piece by piece — not all seven parts thrown at you at once, but three small groups, each explained properly before the next. A quick convention, stated once so nothing has to be guessed later: parts with a solid edge below are registers — tiny stores that each hold exactly one value at a time, living inside the CPU. The part with a dashed edge is memory (RAM) — outside the CPU entirely. It's joined to the CPU by a link you'll meet later in the course. Right now every part except memory is still unmet — dimmed and unlabelled. Match each job below to reveal it.

Meet the two parts that do the CPU's actual work: the decider and the calculator. The CU (Control Unit) is the decider — it works out what each instruction means and sends out the signals that make every other part do its job, in the right order. The ALU (Arithmetic Logic Unit) is the calculator — it does the actual maths and comparisons, but only for an instant. It doesn't remember anything afterwards. "Decodes each instruction and sends out the signals that make every other component do its part, in the right order" is describing the CU — it's the one giving orders. "Does the actual maths and comparisons, but only for an instant" is describing the ALU — it's the one doing the sums.
Ask: is this job about *deciding what happens next*, or about *actually crunching a number*? Only one of the two parts calculates anything at all.
The CU never does maths itself — it's the manager, not the calculator. The ALU never decides what to do next — it just does whatever sum it's handed, then forgets it instantly.

Meet the fetch trio: PC, MAR and MDR — three parts that always work as a team. PC (Program Counter) holds the address of the next instruction to fetch — never the instruction itself, just where to find it. MAR (Memory Address Register) holds an address too, but a different one: the location in memory the CPU is about to read from or write to, right now. MDR (Memory Data Register) holds the actual data or instruction — whatever has just travelled in from memory, or is about to travel out. It never holds an address. Three registers, three jobs: next, where, and what. Tap a job, then tap the part it belongs to.

"Holds the memory address of the next instruction to fetch" is PC — it's always looking ahead. "Holds an address — the location in memory the CPU is about to read from or write to" is MAR — it's the address being used right now, not the next one. "Holds the actual data or instruction that has just travelled in from memory" is MDR — the only one of the three holding a *thing*, not a *place*.
Two of these three hold an address (a place); only one holds the actual value or instruction (a thing). Sort that split first.
MAR and PC are the pair everyone mixes up — PC is always the address of what's coming next; MAR is the address of whatever's being looked up right now. MDR is the odd one out: it never holds an address at all, only the data or instruction that address pointed to.

Two parts left, and they're easy to confuse with parts you've already met. CIR (Current Instruction Register) holds whichever instruction is currently being decoded and carried out. Some books call it the IR — Instruction Register — same thing. ACC (Accumulator) holds the running result of whatever the ALU is calculating right now — the CPU's one working notepad for numbers. It's tempting to think the ALU remembers the answer, since it did the sum. It doesn't — the ALU calculates for one instant, then forgets. ACC is what actually holds on to the result afterwards.

"Holds whichever instruction is currently being decoded and carried out" is CIR. "Holds the running result of whatever the ALU is calculating right now" is ACC. Notice neither job mentions an address at all — by this point in the machine, addresses have done their job and it's all instructions and numbers.
One of these two holds an instruction (a command to obey); the other holds a number (a result so far). That split answers both at once.
CIR holds the instruction itself — the thing being obeyed. ACC holds a number — the running result the ALU keeps adding to. The ALU does the work; ACC keeps the score.

If you're unsure where to start: sort by *place vs thing vs role* first. MAR and PC hold places (addresses). MDR, CIR and ACC hold things (data, an instruction, a number). CU and ALU hold neither — they're roles, not stores: one decides, one calculates.
Work through the groups in the order you met them: the two workers first, then the fetch trio, then the last pair.
CU decides, ALU calculates. PC points at what's next, MAR points at what's happening now, MDR carries the actual data. CIR holds the instruction being obeyed; ACC holds the running number. Seven parts, seven one-word jobs.
