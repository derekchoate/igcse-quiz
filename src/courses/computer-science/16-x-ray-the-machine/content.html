Open up a CPU (central processing unit — the chip that actually runs your programs) built the ordinary way computers have used since the 1940s, and you find two working units and five registers — tiny stores that each hold exactly one value at a time. Here they are, by name: CU (Control Unit), ALU (Arithmetic Logic Unit), PC (Program Counter), MAR (Memory Address Register), MDR (Memory Data Register), CIR (Current Instruction Register — some books call this one the IR, Instruction Register; same thing), and ACC (Accumulator). Tap a job below, then tap the part you think it belongs to — or drag it straight across.

Tap a job to begin.

"Holds an address — the location in memory the CPU is about to read from or write to. Never the data itself, only the location" is describing the MAR. "Holds the actual data or instruction that has just travelled in from memory, or is about to travel out. Never an address" is describing the MDR. Notice those two are easy to mix up precisely because they sound similar — the trick is that one only ever holds a *place*, the other only ever holds a *thing*.
For each job, ask: is this describing a *place* (an address), a *thing* being carried (data or an instruction), or a *role* (something this part always does)? That sorts the seven fairly quickly.
MAR and MDR are the pair everyone mixes up at first — MAR is the *address* (where), MDR is the *data* (what). PC is also an address, but a different one: it's always the address of the *next* instruction, not the one being worked on right now.

Below is a glass CPU — every part see-through so you can watch a value move. A quick convention, stated once so nothing has to be guessed later: boxes with a solid edge are registers living inside the CPU. The box with a dashed edge is memory (RAM) — outside the CPU, reached only by the buses you'll meet properly in Discovery 4. A strip above the log names whichever bus is carrying something at that instant. Press the crank once per step and watch PC especially closely across the whole fetch — something about its timing is easy to assume wrong.

Crank once: PC's address, 100, travels the address bus into MAR. Crank again: PC increments to 101 — already pointing at the NEXT instruction, before this one has even reached the CIR. Crank again: the control unit sends a READ signal along the control bus, telling memory to hand over what's stored at address 100. Crank again: memory sends back the instruction there — "LOAD 200" — along the data bus into MDR. Crank once more: MDR's contents copy into CIR. The instruction has arrived, ready to be decoded — and PC changed two steps before that, not at the end.
Watch PC across one complete fetch. Did it change before or after the instruction arrived in the CIR?
It changes during fetch — it's already pointing at the next instruction while this one is still on its way in. That's the whole point of a program counter: it never falls behind, even mid-cycle.

Picture the CPU has already fetched its next instruction into the CIR: ADD, plus the address where the amount to add is stored. Its accumulator — ACC, the CPU's one working notepad for numbers — currently holds 19, your age. Pick an amount below, start the ADD, then crank through decode and execute.

Set the amount to 5 and press "Start this ADD". Crank once: the control unit decodes CIR — "ADD 201" means add whatever's stored at address 201 to ACC. Crank again: 201 travels the address bus into MAR. Crank again: memory sends back the value there, 5, along the data bus into MDR. Crank once more: the ALU adds MDR's 5 to ACC's 19. ACC updates to 24 — right in front of you. Notice the ALU did the sum, but it's ACC that keeps hold of the answer afterwards; the ALU itself doesn't remember a thing once it's done.
Try a small amount (under 10) and then a large one (15 or more) — does ACC update the same way either time?
It's tempting to think the ALU is where the answer lives afterwards, since it's the ALU that does the actual adding. It isn't — the ALU calculates for one instant and then forgets; ACC is the register that actually holds the running result.

Every value you watched travel in Discoveries 2 and 3 moved along one of exactly three roads. The address bus carries a location in memory — never the value stored there, only where to find it. The data bus carries the actual thing being moved — a number, or an instruction fresh out of memory (an instruction counts as data here; it's just being carried, not obeyed yet). The control bus carries signals and commands only — "read this", "write that" — never a location and never a value. Tap a parcel below, then tap the road you think it travels on.

Tap a parcel to begin.

"The address 104, on its way from PC into MAR" is a location — that's the Address bus. "A READ signal, telling memory to hand something over" is a command with no location and no value attached — that's the Control bus. "The value 24, arriving from memory into MDR" is an actual number being carried — that's the Data bus.
Ask what the parcel actually IS: a place, a thing, or a bare instruction to memory itself?
A place (an address) is always the Address bus. A thing being moved — a value or a fetched instruction — is always the Data bus. A command with nothing else attached, like "read" or "write", is always the Control bus, and only the Control bus.

Here's a tiny three-line program, at the concept level (never mind the exact machine code — that's a later module). Line 1, LOAD 200: copy whatever's stored at address 200 into ACC. Line 2, ADD 201: add whatever's stored at address 201 to ACC. Line 3, STORE 202: copy ACC's value out to address 202. Address 200 holds 19 (your age); address 201 holds 6. Before you crank a single step, take a private guess at what ACC will hold once all three lines have run. Nobody sees this guess but you — there's no wrong answer here, only a chance to check your own thinking against the machine.

Guess: 19

Line 1 fetches, decodes and executes LOAD 200 — 19 copies straight into ACC (no ALU needed, LOAD is just a delivery). Line 2 fetches, decodes and executes ADD 201 — the ALU adds 6 to ACC's 19, making 25. Line 3 fetches, decodes and executes STORE 202 — ACC's 25 copies out to address 202. STORE never changes ACC itself; it only copies ACC's value elsewhere. Final answer: 25.
Work out what LOAD and ADD actually do to ACC, in order, before you crank anything.
LOAD 200 copies 19 into ACC. ADD 201 adds 6 to whatever ACC already holds. STORE just copies ACC's value out to memory — it never changes ACC's value at all.
