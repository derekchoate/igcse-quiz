Every form you've ever filled in has a gate in front of it. Meet the gate.

Picture the guardhouse at the entrance of a housing estate. There's a checklist, a barrier, and a reason given every time something isn't let straight through.

Every system that takes data from a human has the same thing built into its code. It's just invisible: a gate, equipped with checks, deciding what gets in.

This module hands you the checklist. You'll equip a gate, then watch it work on a queue of real entries. You'll discover the one thing it can never catch. Then you'll switch sides — and become the person whose job is to probe someone else's gate, on purpose.

Same deal as always: no marks, no timer, no wrong answers, nothing to hand in. When the gate holds an entry back, that's the gate doing its job. It's never you getting something wrong. Take a nudge whenever you fancy one. Stars can never be taken away.

Cambridge names five basic checks a gate can be equipped with. (A sixth, the check digit, gets its own discovery later — it works differently enough to deserve one.)

Each check catches exactly one kind of problem in typed data, and nothing else.

The five checks
What each one catches

Drag a description across, or tap one and then the check it belongs to.

Presence check pairs with "a required box was left completely empty." It only asks whether anything was typed at all. Type check pairs with "the value is the wrong kind of data." It asks whether the value is the right kind — a whole number, say, not text. Range check pairs with "the value is outside the allowed range." It asks whether a number sits between two limits. Length check pairs with "the value has the wrong number of characters." It counts characters, nothing more. Format check pairs with "the value doesn't follow a required pattern." It looks for a shape — like an @ symbol somewhere in an email address. Each check asks one narrow question, and nothing else. Here they are, in the order they'd run: is it there at all, is it the right kind, is it in range, is it the right length, does it look right.
Start with the check that doesn't care what was typed. It only asks whether anything was typed at all — that's Presence.
Range and Length sound similar, but they check different things. One counts a value's size. The other counts a value's characters. A PIN's length check and an age's range check will never swap places.

Here's the rule, stated exactly. The gate on this Age field carries three checks. Presence means it can't be left blank. Type means it must be a whole number. Range means it must sit between 0 and 120, inclusive.

Six entries are queued up. For each one, make your own call first — Admit or Hold. Then open the gate, and see what actually happens.

Getting your own call wrong isn't a thing here. It's just a moment to notice what you'd have guessed.

Age field, entry 1 of 6

Entry left blank: Presence check fires first. Nothing was typed, so it's held — Type and Range never even get a turn. Entry "twelve": Presence passes, because something's there. Type fails — "twelve" is text, not a whole number — so it's held. Entry −5: Presence and Type both pass. Range fails, because −5 sits below 0. Held. Entry 45: all three pass. Admitted. Entry 150: Range fails again — this time, 150 sits above 120. Held. Entry 0: all three pass. 0 sits inside "0 to 120 inclusive," so it's admitted — even though it's sitting right on the edge.
Checks run in a set order. The first one that fails is the one whose reason gets shown. The gate doesn't list every check that would also have failed.
"Inclusive" is doing real work in this rule. 0 and 120 both count as valid ages here. It's not just the numbers strictly between them.

Validation only ever checks that data is shaped the way a rule expects. It has no way to check that data is true. That gap is exactly what verification exists to close — see how each of these two would have caught it:

See both…

Presence: something was typed — passes. Type: 21 is a whole number — passes. Range: 21 sits inside 0 to 120 — passes. Every check the gate owns says this entry is fine. The gate admits it. But the person who typed it is 12, not 21. The form isn't invalid — it's simply untrue. Validation checked the shape of the data against a rule. It never checked whether the data matched reality, because it never had access to reality in the first place. That's what verification is for. A double entry check types the same value twice, then compares the two. A visual check has a human look at the entered value next to its real source. Both catch things that are perfectly valid — and still wrong.
Run the checks first, and watch every single one pass. That's the whole point of this discovery — not a trick.
Validation can only ever compare data against a rule it already knows. It was never given a way to compare data against the real world. That's a completely different job — and it has a different name.

Switch sides. You're not building the gate now. You're the person whose job is to probe someone else's gate, on purpose — to prove it holds up.

The rule this time: a whole number, 1 to 100 inclusive.

Cambridge names four categories of data worth crafting for a rule like this. Here they are, stated exactly, so there's no guessing:

1. Normal — valid, and nowhere near the edges (say, 45).

2. Extreme — valid, but sitting exactly on an edge (1 or 100).

3. Boundary — invalid, exactly one step past an edge (0 or 101 — the very first values the gate has to reject).

4. Abnormal — invalid, and nowhere near an edge at all (text, or a number miles outside the range).

Type a probe value, and send it in.

Type a probe value, then press Probe.

Light up all four…

Probe 45: ordinary, valid, nowhere near either edge. That's normal. Probe 100: valid, but it's the single largest number the rule still accepts. That's extreme. Probe 101: invalid, and it's the very first number past that same edge. That's boundary. Probe "twenty": invalid, but not because it's near an edge — it's the wrong kind of data altogether. That's abnormal. Notice 100 and 101 sit right next to each other on the number line. They still land in two different categories — one is inside the rule, the other is the first step outside it.
Extreme and boundary both live right at the edges of the rule — but they're not the same thing. The rule says 1 to 100 inclusive. Which two numbers are still valid but sit exactly on the edge? Which two numbers are the very first ones the gate has to reject?
1 and 100 are extreme data. They're valid, but as far out as the rule allows before it would tip over. 0 and 101 are boundary data — the immediate rejected neighbours, one single step past each edge. That pairing — a valid edge value, plus the first rejected value right beside it — is exactly what "boundary" means.

This is the exact barcode from Module 14. It has thirteen digits — the last one outlined in teal. Back then, you learned it catches a misread digit.

It's worth naming properly now. A check digit is the sixth item on Cambridge's validation list. It sits alongside range, length, type, presence and format. But it doesn't look at meaning at all. It's pure arithmetic, worked out from the other twelve digits, then compared.

Tap any of the twelve digits to bump it. Watch the gate react exactly the way it did in Module 14.

Try corrupting…

As printed, the computed check digit matches the printed one. The gate lets it through, with nothing to say. Tap the very first digit once. The computed check digit no longer matches, and the gate reports it instantly — exactly as if a scanner had misread that digit for real. Reset, then try a digit near the end instead. Same result. A check digit doesn't need to know what a barcode number means to catch damage to it. It only needs its own arithmetic to stop matching.
Try an early digit first. Then reset, and try one nearer the end. The check reacts to a change anywhere in the number — not just close by.
Every other check on the gate's list looks at what a value means — its size, its length, its shape. The check digit is the odd one out. It looks at nothing but itself, recomputed — and whether the arithmetic still lines up.

Notice what just happened — a twenty-sixth time

You equipped a gate with five named checks, and matched each to exactly what it catches.

You watched real entries queue up against an Age rule. You made your own call on each one first. Then you saw the checks fire in order — presence, then type, then range.

You met an entry that passed every single check, and was still wrong. That's the exact edge of what validation can ever promise: it checks shape against rule, never truth against reality. That's verification's job.

You stepped into the saboteur's chair. You crafted normal, extreme, boundary and abnormal data for one plain rule. You learned that "right at the edge" and "just past it" are two genuinely different things.

And you met the check digit again. This time, it's properly named — the one check on the whole list that never looks at meaning at all.
