Every form you've ever filled in has a gate in front of it. Meet the gate.

Picture the guardhouse at the entrance of a housing estate — a checklist, a barrier, and a reason given every time something isn't let straight through. Every system that takes data from a human has exactly the same thing built into its code, just invisible: a gate, equipped with checks, deciding what gets in. This module hands you the checklist. You'll equip a gate, watch it work on a queue of real entries, discover the one thing it can never catch, and then switch sides to become the person whose job is to probe someone else's gate on purpose.

Same deal as always: no marks, no timer, no wrong answers, nothing to hand in. When the gate holds an entry back, that's the gate doing exactly what it's built to do — never you getting something wrong. Take a nudge whenever you fancy one. Stars can never be taken away.

Cambridge names five basic checks a gate can be equipped with (a sixth, the check digit, gets its own discovery later — it works differently enough to deserve one). Each check catches exactly one kind of problem in typed data, and nothing else. Drag each check on the left onto the description on the right that matches what it catches — or tap a check, then tap the description.

The five checks
What each one catches

Drag a description across, or tap one and then the check it belongs to.

Presence check pairs with "a required box was left completely empty" — it only asks whether anything was typed at all. Type check pairs with "the value is the wrong kind of data" — it asks whether what was typed is even a whole number, say, rather than text. Range check pairs with "the value is outside the allowed range" — it asks whether a number sits between two limits. Length check pairs with "the value has the wrong number of characters" — it counts characters, nothing more. Format check pairs with "the value doesn't follow a required pattern" — it looks for a shape, like an @ symbol somewhere in an email address. Each check asks exactly one narrow question, in this exact order of narrowness: is it there at all, is it the right kind, is it in range, is it the right length, does it look right.
Start with the one that doesn't care what was typed, only whether anything was typed — that's Presence.
Range and Length sound similar but check completely different things — one counts a value's size, the other counts a value's characters. A PIN's length check and an age's range check will never swap places.

Here's the rule, stated exactly: an Age field, gate equipped with three checks — Presence (can't be left blank), Type (must be a whole number), Range (0 to 120 inclusive). Six entries are queued up. For each one, make your own call first — Admit or Hold — then open the gate and see what actually happens. Getting your own call wrong isn't a thing here; it's just a moment to notice what you'd have guessed.

Age field, entry 1 of 6

Entry left blank: Presence check fires first — nothing was typed, so it's held before Type or Range ever get a turn. Entry "twelve": Presence passes (something's there), but Type fails — "twelve" is text, not a whole number, so it's held. Entry −5: Presence and Type both pass, but Range fails — −5 sits below 0, so it's held. Entry 45: all three pass — admitted. Entry 150: Range fails again, this time above 120 — held. Entry 0: all three pass, because 0 is inside "0 to 120 inclusive" — admitted, even though it's sitting right on the edge.
Checks run in an order, and the first one that fails is the one whose reason gets shown — the gate doesn't bother listing every check that would also have failed.
"Inclusive" is doing real work in this rule — 0 and 120 both count as valid ages here, not just the numbers strictly between them.

Validation only ever checks that data is shaped the way a rule expects. It has no way at all to check that data is true. That gap is exactly what verification exists to close — see how each of these two would have caught it:

See both…

Presence: something was typed — passes. Type: 21 is a whole number — passes. Range: 21 sits inside 0 to 120 — passes. Every check the gate owns says this entry is fine, and the gate admits it. But the person who typed it is 12, not 21 — the form is simply untrue, not invalid. Validation checked the shape of the data against a rule; it was never able to check whether the data matched reality, because it never had access to reality in the first place. That's what verification is for: a double entry check (type the same value twice, compare the two) or a visual check (a human looks at the entered value next to its real source) both catch things that are perfectly valid and still wrong.
Run the checks first and watch every single one pass — that's the whole point of this discovery, not a trick.
Validation can only ever compare data against a rule it already knows. It was never given a way to compare data against the real world — that's a completely different job, and it has a different name.

Switch sides. You're not building the gate now — you're the person whose job is to probe someone else's, on purpose, to prove it holds up. The rule this time: a whole number, 1 to 100 inclusive. Cambridge names four categories of data worth crafting for a rule like this. Stated exactly, so there's no guessing: normal is valid and nowhere near the edges (say, 45); extreme is valid but sitting exactly on an edge (1 or 100); boundary is invalid, exactly one step past an edge (0 or 101 — the very first values the gate has to reject); abnormal is invalid and nowhere near an edge at all (text, or a number miles outside the range). Type a probe value and send it in — light up all four.

Type a probe value, then press Probe.

Light up all four…

Probe 45: ordinary, valid, nowhere near either edge — normal. Probe 100: valid, but it's the single largest number the rule still accepts — extreme. Probe 101: invalid, and it's the very first number past that same edge — boundary. Probe "twenty": invalid, and not because it's near an edge — it's the wrong kind of data altogether — abnormal. Notice 100 and 101 sit right next to each other on the number line but land in two different categories, because one is still inside the rule and the other is the first step outside it.
Extreme and boundary both live right at the edges of the rule — but they're not the same thing. The rule says 1 to 100 inclusive. Which two numbers are still valid but sit exactly on the edge? Which two numbers are the very first ones the gate has to reject?
1 and 100 are extreme data — valid, but as far out as the rule allows before it would tip over. 0 and 101 are boundary data — the immediate rejected neighbours, one single step past each edge. That pairing, a valid edge value plus the first rejected value right beside it, is exactly what "boundary" means.

This is the exact barcode from Module 14 — thirteen digits, the last one outlined in teal. Back then you learned it catches a misread digit. It's worth naming properly now: a check digit is the sixth item on Cambridge's validation list, alongside range, length, type, presence and format — except it doesn't look at meaning at all. It's pure arithmetic, worked out from the other twelve digits and compared. Tap any of the twelve to bump it, and watch the gate react exactly the way it did in Module 14.

Try corrupting…

As printed, the computed check digit matches the printed one — the gate lets it through with nothing to say. Tap the very first digit once: the computed check digit no longer matches, and the gate reports it instantly — exactly as if a scanner had misread that digit for real. Reset, then try a digit near the end instead: same result. A check digit doesn't need to know what a barcode number means to catch damage to it; it only needs its own arithmetic to stop matching.
Try an early digit first, then reset and try one nearer the end — the check reacts to a change anywhere in the number, not just close by.
Every other check on the gate's list looks at what a value means — its size, its length, its shape. The check digit is the odd one out: it looks at nothing but itself, recomputed, and whether the arithmetic still lines up.

Notice what just happened — a twenty-second time

You equipped a gate with five named checks and matched each to exactly what it catches. You watched real entries queue up against an Age rule, made your own call on each one first, and saw the checks fire in order — presence, then type, then range. You met an entry that passed every single check and was still wrong, and found the exact edge of what validation can ever promise: it checks shape against rule, never truth against reality — that's verification's job. You stepped into the saboteur's chair and crafted normal, extreme, boundary and abnormal data for one plain rule, learning that "right at the edge" and "just past it" are two genuinely different things. And you met the check digit again, properly named this time, as the one check on the whole list that never looks at meaning at all.
